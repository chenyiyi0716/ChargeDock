# ChargeDock 技术选型

> 版本：v1 · 状态：方向已定稿 · 关联文档：[产品设计文档](产品设计文档.md)

## 1. 背景与前提

本文件记录 ChargeDock 的技术选型结论与理由。选型基于以下前提：

- **复用** BatteryWatch 已逆向并验证的设备层代码（鼠标 HID、耳机 BLE）。
- UI 先用 **WinUI 3** 做一版，不合适再换回 **WPF**。
- 认真重做一版，不迁就现有电脑环境，以合适的技术栈为准。
- 部署形态为**安装 EXE**。
- 仅 Windows 单机个人使用：无账号、无跨平台、无多品牌通用适配。

## 2. 结论：技术栈总览

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 语言 | C#（**.NET 8 LTS**） | 直接承接现有设备层，零语言迁移成本 |
| UI 框架 | **WinUI 3**（Windows App SDK，≥1.6） | 优先方案；不合适则换 WPF |
| 设备访问 | 复用现有代码，抽成独立类库 | BLE 走 `Windows.Devices.Bluetooth`；HID 走 SetupAPI P/Invoke |
| 托盘图标 | `Shell_NotifyIcon` P/Invoke 或 WinForms `NotifyIcon` 互操作 | WinUI 3 无原生托盘；图标为 GDI+ 自绘**环形仪表**，右键菜单为**自绘玻璃菜单**（非原生 ContextMenuStrip） |
| 部署 | 非打包（unpackaged）+ 自包含（self-contained），打成**安装 EXE** | 开机自启写 Run 键，与现有一致 |
| 测试 | xUnit + 设备层抽象为接口 | 补上现有「无单元测试」的技术债 |

## 3. 选型理由

### 3.1 决定技术栈的是设备层，不是 UI

ChargeDock 的界面由「托盘图标 + 右键菜单 + 一张圆角卡片 + 设置页」组成（见 UI 设计文档），任何栈都能做。真正的难点集中在设备数据通道，且全部是 Windows 原生接口：

| 设备 | 数据来源 | 技术栈要求 |
| --- | --- | --- |
| 鼠标 HECATE G3M Pro | 2.4G 接收器私有 HID 广播 + 主动查询帧 | 裸 HID 读写（SetupAPI / `HidD_GetInputReport`） |
| 键盘 K820 | 固件不上报电量 | 无解，先搁置 |
| 耳机 REDMI Buds 8 Pro | BLE GATT `0x180F` / `0x2A19`；经典蓝牙侧私有通道 | WinRT 蓝牙 API |

即 90% 的工程量在 Windows 原生设备访问上，选型必须围绕「谁访问 Windows 设备 API 最顺」来定。

### 3.2 为什么是 C# / .NET

1. **设备层有一等公民官方 API**：BLE 用 `Windows.Devices.Bluetooth`，HID 用 `Windows.Devices.HumanInterfaceDevice` 或 P/Invoke SetupAPI，无需第三方库去猜蓝牙 / HID 协议栈的坑。
2. **本仓库已证明可行**：`HecateHid.cs` 的鼠标校验算法、`Ble.cs` 的蓝牙地址枚举均已跑通，换栈等于把最脏的部分全部重写，没有收益。
3. **形态匹配**：托盘图标、置顶悬浮窗、开机自启、气泡通知都是 .NET + Windows API 最成熟的场景。
4. **升级到 .NET 8 顺理成章**：BLE 在 .NET 8 里是 CsWinRT 原生投影，比现在 .NET Framework 4.0 的 winmd 互操作更干净；`HecateHid.cs` 的 SetupAPI P/Invoke 是纯平台调用，基本不动即可编译。

### 3.3 为什么先试 WinUI 3

- 微软当前桌面主线，现代控件、主题、动效均优于 WPF，契合「认真重做」。
- 与「复用设备层」正交：UI 本来就要重写，WinUI 3 是成本最低的「现代壳」。

## 4. 关键架构决策：设备层独立类库 + 接口抽象

这是「先试 WinUI 3、不行换 WPF」能真正低成本落地的前提，强烈建议第一步先立此边界：

- 将设备访问抽成独立的 **`BatteryWatch.Devices`** 类库，对外只暴露一个 `IBatteryReader` 接口（鼠标 / 耳机 / 键盘各一个实现）。
- UI 项目只依赖该接口，不碰任何 Windows 设备 API。
- WinUI 3 与 WPF 各是一个「薄壳」：切换时**只换 UI 项目，设备层一字不动**。

```
ChargeDock/
├─ src/
│  ├─ Devices/            # 设备层（复用 BatteryWatch 逆向成果）
│  │  ├─ IBatteryReader.cs
│  │  ├─ MouseReader.cs   # HID / 2.4G 私有协议
│  │  ├─ HeadsetReader.cs # BLE GATT
│  │  └─ ...
│  ├─ App.WinUI3/         # UI 壳（优先）
│  └─ App.Wpf/            # UI 壳（兜底，按需）
```

## 5. UI 框架的三个已知坑（「换回 WPF」的潜在导火索）

1. **托盘图标是 WinUI 3 最别扭的地方**：无原生托盘控件，需自己 P/Invoke `Shell_NotifyIcon` 或借 WinForms `NotifyIcon`。托盘是 ChargeDock 的核心入口，这一步体验不好即是「换 WPF」的头号理由。
2. **体积明显变大**：现 demo 是 50KB 单文件；WinUI 3 自包含需带 Windows App SDK + .NET 运行时，达几十 MB。对「轻量、不打扰」的常驻小工具是可接受的现实，但需提前知晓。
3. **WinUI 3 的 XAML ≠ WPF 的 XAML**：控件命名、样式系统均有差异，现有 `Program.Ui.cs` 那套 WPF 写法不移植——它本就是要被重写的部分。

**换回 WPF 的触发条件**：托盘互操作体验差、运行时部署麻烦、或卡片置顶 / 定位出现怪癖。

## 6. 部署：安装 EXE

### 6.1 形态

应用本体采用**非打包（unpackaged）+ 自包含（self-contained）**发布，再由**安装 EXE** 分发。理由：MSIX 打包应用的开机自启受限（StartupTask 有限支持）且托盘行为别扭；非打包 + 自包含的单目录应用与现有部署方式一致。

### 6.2 安装器方案（推荐：自研轻量安装器）

延续现有 `Setup.cs` 的思路，产出一个单文件安装 EXE：

- 释放主程序到 `%LOCALAPPDATA%\Programs\ChargeDock\`。
- 创建桌面快捷方式与开始菜单快捷方式。
- 写入卸载信息（「设置 → 应用」可见「ChargeDock」）。
- 支持静默安装 `/silent` 与卸载 `/uninstall`。
- 安装完成后自动启动程序。

优点：零第三方依赖、体积小、与「轻量不打扰」的产品定位一致，且现有实现已验证。

### 6.3 备选：Inno Setup

若后续需要标准向导式安装界面（许可证页、安装路径选择等），可切到 Inno Setup，产物仍为单文件 EXE。代价是引入一套脚本工具链、产物体积略增。当前阶段不采用。

## 7. 测试策略

- 设备层通过 `IBatteryReader` 接口注入，业务逻辑（低电量判断、设备显示规则）可脱离真机做单元测试。
- 采用 **xUnit** 编写单元测试，弥补现有「靠 `--selftest` 手工验证、无单元测试」的债。
- 保留 `--selftest` / `--render` 这类不开界面的诊断入口，作为真机联调的辅助手段。

## 8. 明确不做 / 后续

- 不做账号与付费、多品牌通用适配、跨平台（与产品边界一致）。
- 历史电量曲线、更多主题配色、电量估算与校准为后续规划，本期不纳入。

## 9. 下一步

1. 立目录结构与项目拆分（`Devices` 类库 + UI 壳）。
2. 抽 `IBatteryReader` 接口并迁移设备层代码。
3. 搭 WinUI 3 空壳，优先验证托盘图标与置顶卡片。
4. 视验证结果决定是否切换到 WPF 壳。
